# 验证任务工单编写标准

验证任务工单按照`stage2.md`的格式组织，由“文档概述 + 四个主体部分 + 审核记录”组成。后续Stage可直接沿用该结构，仅调整具体任务内容。

## 一、文档概述

本部分位于四个主体部分之前，需要描述：

- 前一Stage已经完成的功能和当前基线。
- 本Stage需要新增的总体能力。
- 如果分为A/B阶段，说明各阶段职责和完成标志。
- 本Stage支持什么、不支持什么，以及保留的已知限制。

注意事项：必须区分“代码完成、编译通过、功能测试通过和最终冻结”，能力边界应明确、可检查。

# 第一部分：本Stage需要完成的任务

本部分描述“要实现什么”，主要包括：

## 1. 协议和通道能力

- 各通道需要新增的发送、接收和监测能力。
- 每个信号的驱动方和唯一所有者。
- VALID、READY、payload、LAST和响应的具体时序。
- reset、stall和握手完成后的信号行为。

## 2. 时序数值生成机制

- 使用哪些generator或配置对象。
- generator实例如何划分，是否允许共享。
- delay/gap由谁生成、保存在哪里、由谁消费。
- 固定、随机或burst模式的配置方法。

## 3. 事务和并行能力

- 支持的事务类型、burst类型和长度范围。
- 通道之间允许的先后关系。
- 读写是否可以并行。
- outstanding、乱序和交织等限制。

注意事项：任务描述应落实到具体握手和周期行为，不能只写“支持某功能”。

# 第二部分：测试点、时序约束和协议检查

本部分描述“如何证明实现正确”，主要包括：

## 1. 时序语义

- delay和gap从哪个事件开始计数。
- 数值为0、1和大于1时分别表示什么。
- 第一个beat和后续beat的计数差异。
- READY延迟和VALID延迟是否叠加。

## 2. 功能测试点

- 基本功能、边界值和典型值。
- burst长度、类型和数据模式。
- READY早于、晚于或同周期出现的场景。
- stall、通道顺序、读写并行和Monitor重建场景。

## 3. 协议断言

- 断言部署在哪些接口。
- stall期间稳定性、X/Z、LAST、beat数量和因果关系检查。
- 哪些检查属于Assertion，哪些属于Checker或Driver。
- 正向无误报和负向故意触发的测试方法。

## 4. Reset和异常场景边界

- 本Stage必须验证的reset行为。
- 明确不验证的运行时reset或复杂异常场景。
- 未覆盖场景计划在哪个后续Stage实现。

注意事项：随机测试不能代替必须确定命中的定向测试；负向断言测试必须与正常回归隔离。

# 第三部分：各组件需要完成的内容

本部分描述“代码具体改在哪里”，主要包括：

## 1. 组件修改总览

- 用表格列出每个组件的当前能力和目标能力。
- 标明新增、修改、保留或删除的组件。

## 2. 公共对象和Transaction

- generator、request、response和event需要增加的字段或约束。
- 数组长度与LEN、beat数量的对应关系。
- 公共宏、typedef和参数的存放位置。

## 3. Driver

- 每个长期线程及其信号所有权。
- item clone、队列、`item_done()`和上下文释放规则。
- 各通道发送、接收、READY和reset处理方法。

## 4. Monitor

- 按握手发布哪些channel event。
- 如何重建完整request和response。
- 不完整burst、LAST错误和reset时如何清理状态。

## 5. Sequence、Sequencer、Agent和Cfg

- Master sequence产生什么请求和时序值。
- Reactive Slave sequence如何接收真实请求并返回响应。
- Sequencer FIFO、Agent active/passive和cfg职责。
- sequence文件与test文件的调用关系。

## 6. Checker

- Checker的定位和输入TLM端口。
- Expected和Actual的真实来源。
- channel event、完整request和response的比较字段。
- ID转换、顺序、因果关系、计数和结束pending检查。
- 明确哪些内容不属于Checker。

## 7. TLM和文件组织

- 用连接图说明sequence、driver、interface、monitor和checker的数据流。
- 说明`common`、`env`、`seq`、`tc`和`tb`目录职责。
- 给出实施后的目标目录树。
- 说明package include/import和filelist编译顺序。

注意事项：组件职责不能重叠；sequence放在`dv/seq`，test放在`dv/tc`；目录树必须与最终代码同步。

# 第四部分：验证和验收

本部分描述“怎样判定Stage完成”，主要包括：

## 1. 代码审核

- 代码风格、组件结构和能力边界检查。
- 编译、elaboration及warning要求。
- 是否误实现后续Stage功能。

## 2. 分项功能测试

- 按功能分别列出burst、delay/gap、READY、顺序、并行等验收项。
- 每一项写清输入组合、预期现象和通过条件。

## 3. 协议断言验收

- 正向回归必须零非预期断言。
- 负向自测必须命中指定断言。
- 预期触发与真实测试失败的区分方法。

## 4. 端到端测试清单

- 列出所有独立testcase及其对应sequence。
- 列出需要继续运行的前一Stage回归。
- 每个test只配置本场景并调用相应sequence。

## 5. 端到端检查结果

- event、完整transaction、ID转换和数据内容全部匹配。
- 没有重复、遗漏或额外事务。
- 队列、FIFO和事务上下文全部清空。
- `UVM_WARNING`、`UVM_ERROR`和`UVM_FATAL`满足要求。

## 6. 运行入口和回归要求

- 编译、单测试、Stage回归、完整正向回归和断言自测命令。
- 日志、波形和覆盖率输出路径。
- Makefile参数、test名称和失败退出规则。

## 7. Stage完成条件

- 汇总所有必须同时满足的条件，形成编号清单。
- 条件必须可以通过代码、日志或测试结果直接判断。

注意事项：没有实际运行的验收项不能标记为通过；运行命令必须与当前Makefile和filelist一致。

## 审核记录

工单最后保留审核记录，实施前后持续更新：

- 每个关键决策的状态和说明。
- 实际修改的文件和最终项目目录。
- 工具版本、运行命令和测试列表。
- PASS/FAIL结果、日志及波形路径。
- 遗留问题、保留限制和最终冻结状态。

审核记录是实际结果，不重复填写计划内容。代码或范围发生变化时，需要同步更新相关任务、测试点、目录树和完成条件。
