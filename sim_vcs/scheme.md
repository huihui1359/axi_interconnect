**第一部分，参数传递方式与输出组织。**

参考的 `test=... dump=y cov=y` 用法可以沿用，主要改进 seed 的含义、参数优先级和运行目录隔离。

建议把参数分成三层：

| 层次 | 典型参数 | 作用 |
|---|---|---|
| 构建参数 | RTL 配置、define、coverage/debug 插桩、工具版本 | 决定需要哪一份可执行文件 |
| 运行参数 | test、seed、verbosity、dump、事务数、背压范围 | 决定一次仿真如何运行 |
| 回归参数 | suite、nseeds、jobs、运行时间上限、遇错是否停止 | 决定批量任务如何展开和调度 |

这样，改变 seed 或事务数量通常不应重新编译；改变 RTL 参数或覆盖率插桩则必须选择相应构建。

对外接口建议如下：

| 参数 | 建议含义 |
|---|---|
| `test` | 单个 UVM 测试类名 |
| `suite` | 一组测试及其运行配置，与 `test` 二选一 |
| `seed` | 数字表示固定 seed，`auto` 表示自动生成并记录 |
| `nseeds` | 每个测试运行多少个 seed，默认 1 |
| `dump` | 保留 `y/n` |
| `cov` | 保留 `y/n`，同时决定构建和运行的覆盖率设置 |
| `verbosity` | 统一接受 UVM 日志等级 |
| `jobs` | 最大并行仿真数量 |

seed 的规则需要明确：

- 单次运行 `seed=100`：只使用 100。
- 回归运行 `seed=100 nseeds=3`：使用 100、101、102。
- `seed=auto nseeds=3`：调度前一次性生成并记录三个数字，再启动任务。
- 每个测试使用明确的 seed 表，不能根据它在整个测试列表中的位置分配 seed，否则新增一个测试就可能改变其他测试的 seed。

`rand=y/n` 可以保留为兼容入口，但只表示**自动生成 seed**，不能表示“是否运行随机测试”。随机测试使用固定 seed，依然是随机测试，只是能够复现。

参数优先级建议统一为：

> 用例默认配置 → 回归集合中的配置 → 命令行显式覆盖。

普通参数按这个顺序覆盖；重复指定相互矛盾的测试名、seed、输出目录等关键参数，应直接报错，避免额外 plusargs 悄悄覆盖调度器已经记录的信息。

输出目录方面，保留当前 `build/log/wave/cov` 分类，但建议为后续并行回归增加**每次运行独立的工作目录**：

```text
work/
  build/<build_id>/                    可复用的编译产物、编译日志
  run/<batch_id>/<run_id>/             运行配置、结果、复现命令、工具辅助文件
  log/<batch_id>/<run_id>/sim.log
  wave/<batch_id>/<run_id>/wave.fsdb
  cov/<build_id>/<batch_id>/<run_id>.vdb
  cov/<build_id>/reports/<report_id>/
```

这里有三个标识：

- `build_id`：区分源码、工具版本及编译配置不同的构建。
- `batch_id`：区分一次单测或一次回归批次。
- `run_id`：区分具体测试、运行配置、seed 和重复尝试。

这样，同一个 test、同一个 seed 连跑两次也不会覆盖；多个仿真不会争用 `ucli.key`、PLI 日志等默认文件。构建可复用，每次仿真各自进入独立目录运行。

每次运行至少记录测试名、完整配置、实际 seed、构建标识、源码版本及工作区修改状态、工具版本、执行命令和最终结果。**seed 是复现条件之一，还需要对应的源码、工具和配置。**

覆盖率也建议每次运行独立收集，结束后合并兼容的数据库；波形默认关闭，定位失败时用原配置和 seed 重跑取波形。重跑成功不能抹掉首次失败记录。

所以，对参考方案我的意见是：**保留简单参数和 work 隔离的思路，改进 seed、构建复用、运行隔离及结果记录。**

**第二部分，测试的分类、组织与运行方式。**

重新看源码后，我不建议简单地把当前测试切成“原来 26 个定向＋新增 4 个随机”。

更合理的是用两个维度描述激励：

| 维度 | 取值示例 | 回答的问题 |
|---|---|---|
| 场景组织 | 定向、随机 | 事务组合、读写选择等由预设场景还是随机过程决定？ |
| 时序扰动 | 固定、随机 | READY、响应延迟、通道间隔是否随机？ |

按主要验证意图，当前 30 个测试可以这样组织：

| 构成 | 数量 | 说明 |
|---|---:|---|
| 定向场景，固定或明确安排时序 | 23 | 基础读写、burst、顺序、ID、路由、仲裁等 |
| 定向场景，随机时序扰动 | 2 | `tp_backpressure_outstanding`、`tp_backpressure_random_stage2_smoke` |
| 随机事务或随机场景选择 | 5 | `tp_route_matrix_random`，以及四个较长的 `tp_*_random` 测试 |

例如，短背压冒烟测试发送的地址、ID、burst 长度等有明确安排，主要随机化各通道延迟；它和 `tp_backpressure_outstanding` 都适合归为“定向场景＋随机时序”。分类应根据行为，而非类名里是否出现 `random`。

再给每个测试附加功能标签，例如：

```text
basic、burst、ordering、sid、outstanding、
routing、arbitration、backpressure、concurrency、progress
```

一个测试可以有多个标签，不必强行归入唯一功能目录。以后就能选择“所有 outstanding 相关测试”，而不用记住它们属于哪个开发阶段。

还有一个当前构成上的限制需要明确：四个长随机测试的公共配置，默认只生成单 beat，读写 outstanding 上限也分别为 1。见 [axi_cr_cfg.sv](/home/moxiao/work/axi_interconnect/dv/seq/axi_cr_cfg.sv:70)。因此，增加 seed 并不能自动获得随机 burst 或更深 outstanding 的覆盖；这些能力需要随后扩展激励模型。

运行组织上，建议建立以下测试集合：

| 集合 | 目的 | 初始运行策略 |
|---|---|---|
| `smoke` | 快速确认构建、基本通路和检查机制正常 | 精选约 8 个短测试，各一个固定 seed |
| `directed` | 检查明确的功能场景和边界 | 当前 25 个定向场景；随机时序用例可增加少量 seed |
| `random` | 探索事务和时序组合 | 选择随机事务、随机时序测试，执行多个 seed |
| `nightly` | 日常完整回归 | 全部定向场景＋多 seed 随机测试 |
| `closure` | 补齐具体覆盖缺口 | 按功能标签、约束配置和覆盖目标组织 |
| `selftest` | 检查验证组件自身 | 六个独立 top，使用各自的成功判据 |

这些集合允许重叠。例如，一个基础读测试同时属于 `smoke` 和 `directed`；一个随机背压测试同时属于 `random` 和 `nightly`。

`smoke` 可以先从基础读写、burst 读写、路由矩阵、同 ID 顺序、写仲裁和短背压扰动中各选代表。`nightly` 的随机 seed 数量可以从每项 10 个起步，再根据实测耗时和覆盖增益调整，不必一开始把所有测试都重复 20 次。

回归执行策略建议与单步调试区分：

- 调试单个测试时，可以遇错立即停止。
- 正式回归默认继续运行其他独立任务，最终汇总所有失败。
- 编译失败等公共前提不成立时，停止受影响的任务。
- 仿真进程退出状态、测试完成标记、UVM 错误、检查器结果和超时共同决定结果。

覆盖率目标也需要分清层次。比如当前背压测试要求每个 seed 都命中全部 stall 区间：

- 如果这是该测试必须构造的场景，就应该加强激励，保证场景发生。
- 如果它是多个随机 seed 共同完成的统计覆盖目标，就应在回归批次汇总后判断。

不能仅通过减少事务数、跳过检查，把“没完成覆盖要求”变成通过。现有背压和 SID 测试的问题应保留可见记录，再决定它们进入稳定回归的条件。

为了持续扩展，我建议让 **Makefile 负责启动工具，用例清单负责描述测试，回归清单负责选择测试和配置**。例如，用例清单记录：

```yaml
test: tp_backpressure_outstanding
kind: uvm
scenario: directed
timing: random
tags: [outstanding, backpressure, ordering]
```

这里的字段只是方案示意。未来新增测试时，完成 UVM 注册、编译清单和用例元数据登记，就能按标签加入相关回归，无须继续向 Makefile 添加新的测试列表和循环。

对应的命令接口可以是：

```bash
# 调试单个测试
make run test=tp_backpressure_outstanding seed=17 dump=y

# 快速回归
make regress suite=smoke

# 随机回归，使用明确的种子序列
make regress suite=random seed=100 nseeds=20

# 单个随机测试的多 seed 回归
make regress test=tp_concurrency_random seed=auto nseeds=20
```

以上都是拟议接口。兼容性上保留现有测试类名和常用参数；`SEED`、`TEST` 等作为别名，`reg_times` 映射为 `nseeds`。后续的新定向测试、随机测试和不同配置，都通过清单扩展，不再依赖 stage 编号来组织。
